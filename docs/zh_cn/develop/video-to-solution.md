# 从解谜视频制作语义解法

本流程用于把完整的盘面解密通关视频转为 MaaSVWB 解法。视频提供操作顺序，
制作过程仍需核对每一步前后的手牌、场上对象及目标。解法格式以
[人工解法格式](../solution-format.md)、`assets/schemas/solution.schema.json`
及 `agent/solution_engine/` 的当前实现为准。

**日常新关先读[新聊天最小入口与提示词](./video-solution-start.md)**，本文件用于按需查阅细节。
每关完成后把简短交接摘要放到该关 `evidence.md` 顶部；下一聊天使用文件交接，
无需复制之前聊天或其他关的研究记录。

## 工具准备与日常命令

在仓库根目录执行一次：

```powershell
./tools/setup_video_tools.ps1
$videoPython = '.ai-tools/video/Scripts/python.exe'
& $videoPython tools/puzzle_video.py doctor
```

安装脚本建立独立的 `.ai-tools/video/` 环境，安装下载、图片处理与 Schema 校验依赖，
检查 PATH 中的 FFmpeg / ffprobe。它不会自动安装系统级 FFmpeg。
依赖版本范围记录在 `tools/requirements-video.txt`，不进入产品运行依赖。

下载明确的一个分 P：

```powershell
& $videoPython tools/puzzle_video.py download `
    'https://www.bilibili.com/video/BV1V64R6UE6d' --part 5
```

输出到 `artifacts/puzzle-video/BV1V64R6UE6d_p5/`。一次只下载指定分 P，
`--part` 优先于链接查询参数。默认匿名下载画面流，需要音频时加 `--audio`。
下载器的完整元数据和日志保存在 `source/`，精简来源记录为 `source.json`。
本工具不读取浏览器 Cookie；若匿名画质不足，可按
[yt-dlp 官方文档](https://github.com/yt-dlp/yt-dlp)和
[Cookie 说明](https://github.com/yt-dlp/yt-dlp/wiki/FAQ#how-do-i-pass-cookies-to-yt-dlp)
另行使用用户授权的登录方式。本次匿名下载成功不保证所有视频均可匿名取得相同画质。

粗抽帧、去重和带时间戳的概览：

```powershell
& $videoPython tools/puzzle_video.py prepare `
    artifacts/puzzle-video/BV1V64R6UE6d_p5/source/BV1V64R6UE6d_p5.mp4 `
    --output artifacts/puzzle-video/BV1V64R6UE6d_p5
```

本地已有视频直接使用 `prepare`，不需要重新下载。下载文件的实际扩展名以
`source/` 中结果为准，未必都是 `.mp4`。

只补读不确定的片段：

```powershell
& $videoPython tools/puzzle_video.py prepare `
    artifacts/video-research/BV1V64R6UE6d_p6.mp4 `
    --output artifacts/puzzle-video/BV1V64R6UE6d_p6 `
    --start 43 --end 49 --interval 0.25 --width 1920
```

可加 `--crop X Y W H` 裁剪源画面的区域。默认每 2 秒取一个源帧、宽度上限 1280；
源帧率决定实际可用时间点。通过 FFmpeg `showinfo` 保存源帧 PTS，
不按图片序号推算时间。每次运行建立独立 `runs/frames-*/` 子目录，保留全部
采样图片、时间清单和日志，不覆盖先前素材及人工笔记。

概览按灰度差异过滤相近帧，同时保留首尾和默认每 8 秒的上下文帧。
`--threshold 0` 可关闭去重。去重只能帮助找片段，可能遗漏细小目标线或数值变化；
必须对有效操作补读原始样本。一次最多请求约 600 个采样点，长视频按关卡切分。

校验候选 JSON：

```powershell
& $videoPython tools/puzzle_video.py validate `
    artifacts/video-research/drafts/spec_castorotte_01.json `
    artifacts/video-research/drafts/spec_castorotte_02.json
```

此命令只检查当前 Schema、解法加载器及已填写的序号/数量边界，不执行设备操作，
不自动加入目录，不证明操作或通关成功。下载、抽帧和校验脚本均不调用模型。

## 固定制作流程

1. **确认关卡。** 记录 BV、P、版本、题名、目录 ID、目标、初始手牌和双方占位。
   区分“学习”和“熟练运用”，以及护符主教1/2等重复分组。
2. **本地粗抽帧。** 先每 1–2 秒抽一帧，生成概览，寻找初始盘面、有效操作、
   动作结算和完成状态。抽帧本身不调用模型；发送给模型的图片才进入模型输入。
   先选少量概览，避免把几十张重复的加载帧、动画帧全部输入。
3. **局部细读。** 对出牌、目标线、进化和模式窗口附近改为每秒 4–5 帧。
   每个有效动作保留动作前和结算后证据；必要时读取原始 1080p 帧或局部裁剪。
   仅凭缩略图看不清的手牌数、目标、按钮和牌名标记为待确认，不猜测。
4. **先写状态表。** 每行记录“时间段、动作前手牌数及序号、双方占位、目标、
   动作后变化、证据帧、确定程度”。目标及手牌序号都使用当前从左到右的 1 基序号。
   同时记录护符占位、抽牌、回手、额外召唤、离场重排和自动进化。
   视频版本与实机不同时，先核对费用、身材、进化效果和当前初始状态；离场结果
   可能改变后续序号。看到进化动画时，必须核实触发来源（手动按钮/进化球，还是已有纹章），
   不凭动画本身推断自动进化。
5. **压缩成固定语义步骤。** 查看卡牌、取消选牌、鼠标停留、无效尝试和加载不作为动作。
   卡牌/主战者能力导致的自动进化也不增加 `evolve`；手动进化才增加。
   使用现有的 `play_card`、`attack`、`select_choice`、`select_target`、
   `evolve`、`activate_amulet` 等，不从 PC 录像抄安卓坐标。
6. **检查随机结果下的成立条件。** 盘面解密应寻找一套固定操作顺序。
   随机破坏后，判断后续动作是否对每种剩余对象都有效。
   必须区分“数量改变”和“目标身份改变”：实时计数只解决数量/布局，
   无法选择特定身份；如果后续必须选中某张特定牌，需要重新分析固定解法，
   不能把录像中的一次随机结果当作保证。
7. **生成候选 JSON。** 不增加 Schema 未支持的 `timestamp`、`confidence` 等字段；
   它们放在独立证据文件。`label` 解释动作目的，`after_ms` 留出效果结算时间。
   可以用 `change_roi: battle_board` 检查画面变化，但变化不等于动作成功或动画结束。
   自动数量识别仅适用于对应一侧全部是随从的情况；混有护符时显式计入全部占位。
8. **静态校验。** 同时用 JSON Schema 和 `Solution.from_dict` 加载候选稿。
   再逐行复核状态表中的计数、序号和动画时序；Schema 通过不能代替这个检查。
9. **模拟器验收并接入。** 在获授权的 1280×720 安卓模拟器中从重置盘面执行，
   保存逐步日志和失败前后截图，确认完成状态及返回列表。随机关重复重置验证，
   同时保留随机结果仍然成立的理由，不能用有限次成功代替穷尽证明。
   纳入正式资源后运行 `python tools/generate_interface.py` 及 `tools/test.ps1`。

实际等待参数应根据结算后状态决定。视频间隔还包含作者思考时间，不能直接当成
必要的等待时长。通用流程中的视频来源与示例路径可替换为任意关卡。

## 优化：只让模型处理必要证据

| 环节 | 默认做法 | 避免的重复工作 |
| --- | --- | --- |
| 初始化 | 复用安装好的工具和当前规范；环境异常或规范变化再检查 | 每关安装依赖、重读整个仓库 |
| 下载 | 先列出关卡与已有解法，只处理目标分 P | 把已有解法的整段视频再分析一遍 |
| 粗读 | 本地采样与去重，先读少量概览定位有效区间 | 向模型发送全部加载、停留及重复动画帧 |
| 细读 | 每个动作保留必要的前后状态帧，相邻动作共用状态帧 | 每次重新发送整段视频图片 |
| 字迹 | 全局图确认位置，小区域原尺寸裁剪确认文字 | 为一个卡名反复读取整张 1080p 图；一味缩小导致误读 |
| 卡牌效果 | 只查影响当前步骤的卡名/效果；本地 OCR 结果需与图片核对 | 把整份卡库、全部 OCR 输出塞入上下文 |
| 中间结果 | 每关落盘状态表、确认结论及待补读片段 | 在后续轮次重建已经确认的状态 |
| JSON | 复用同类解法结构，脚本做机械校验 | 让模型反复人工检查格式和范围 |
| 工具输出 | 默认只返回统计、结果路径及失败摘要 | 输出完整下载信息、整份规范或成功测试日志 |
| 多关处理 | 同批复用规范，逐关保存结果；新上下文只带简短交接和目标关材料 | 长期携带前面所有关的图片与研究过程 |

模型默认按用户指定的 6.1 Sol 执行。任务说明限制为状态表、候选 JSON、成立依据及
未解决问题；只有出现目标/效果歧义时才增加局部分析。不要为了降低 token 跳过
必要证据、实机验收或仓库要求的 `tools/test.ps1`；节省测试日志输入即可。
以上措施尚无固定节省百分比，不应把“少发一半图片”直接解释为“节省一半额度”。

## 每关的交付文件与恢复点

脚本自动创建 `drafts/`、`evidence.md` 和 `usage-template.json`，不会生成假解法。
人工/模型在以下模板上填写；每个阶段完成后更新证据状态：

```text
artifacts/puzzle-video/<BV>_p<P>/
  source/                 原视频、下载日志和完整元数据（仅本地）
  source.json             精简来源信息
  runs/frames-*/
    frames/               全部采样帧
    frames.json           源时间、图片路径及是否进入概览
    overview_*.jpg         带时间标签的概览
    ffmpeg.log            本地抽帧诊断
  evidence.md             初始状态、逐步状态表、随机成立依据、待补读区间
  usage-template.json     用量记录模板；未知值保持 null
  drafts/<solution_id>.json  分析后填写的候选解法
```

状态依次为：素材已准备 → 视频证据已核对 → 静态校验通过 → 实机完成已验证。
中断后先读 `evidence.md` 及当前候选，只恢复未完成的步骤。
原视频、完整元数据、登录信息及抽帧留在 Git 忽略目录；正式解法和精简说明按正常
项目流程入库。换机器或清理 artifacts 前，另行保留需要继续使用的本地证据。

通关报告至少说明：源链接与分 P、目录 ID、有效步骤数、随机成立依据、
静态检查结果、实机执行状态，以及仍未确认的事项。

## 给 6.1 Sol 的固定输入与预算

建议每关输入只包含：当前解法规范的相关段落、一份相近示例、关卡元数据、
筛选后的动作前后关键帧、必要的卡牌文字及上一轮未解决问题。
不要为每关重读整套项目说明、卡库和视频全帧。

固定任务提示可使用：

> 根据这些有时间标记的帧，先列每一步执行前后的状态表，再输出符合当前
> MaaSVWB Schema 的固定语义解法。所有序号以动作执行时的盘面为准。
> 区分主动操作、自动进化、查看卡牌和取消操作。检查随机结果是否都能沿用
> 同一套后续步骤，实时数量识别不能代替身份选择。缺乏证据时列出需要补读
> 的时间段，不猜测。证据时间和不确定性写在旁文件，不扩展解法字段。
> 输出候选 JSON、成立依据及待实机验证事项。

早期的每关 8–70k、普通关 25–30k 预算未经实测支持，现已撤回，不能用来承诺后续消耗。

卡特斯罗特超越者1的两轮制作/验收，会话日志均标记为 `gpt-6.1-sol`。
按各轮前后累计计数差值统计（不含此前工具准备及后续用量问答）：

| 项目 | 实测 token |
| --- | ---: |
| 输入总量 | 10,814,688 |
| 其中缓存输入 | 10,489,856 |
| 非缓存输入 | 324,832 |
| 输出（已含推理） | 17,126 |
| 累计总量 | 10,831,814 |

输出中的推理为4,530，已经计入输出，不重复相加。累计总量包含多轮重复携带的
长会话输入，并非一次上下文长度；缓存命中也仍然属于累计输入。
本次有手动/自动进化判断纠正、版本差异和OCR范围修复，不能当成普通新关的稳定成本。
记录保存在该关 `usage-run.json`，实际底层路由与消费额度仍以客户端提供的资料为限。

措施是新聊天只读取最小入口、目标关材料和必要规范；将已确认状态保存到文件，
后续只补缺失证据。尚未有短上下文新关的独立对照数据，因此不宣称能降到固定数值。
至少完成三关同模型、同设置的新聊天样本后，再报告中位数、范围及实机修正次数。

下载、FFmpeg抽帧、静态校验无需LLM调用；返回给模型的日志和图片仍计入输入。
脚本输出尽量只保留统计、文件路径和失败摘要。完整日志本地保存，按需搜索。

## 5 小时额度的测量方法

Token 预估和账户额度百分比分别记录。用量查询给出账户窗口的累计百分比，
没有提供每个模型或每个关卡的分项，不能把一次查询值视为本任务消耗。

1. 在新关分析开始前记录时间、窗口重置时间、已用百分比、指定模型、推理强度与速度设置。
2. 完成该关后再次记录，同一窗口内且没有其他并行用量时，用“结束值减开始值”
   估计该关消耗的百分点。窗口跨重置、其他聊天同时运行或统计尚未更新时，标为不可归因。
3. 中途切换模型时分段记录；请求模型与实际调用模型分别保存。拿不到实际模型就保持未知，
   不根据界面切换时刻推断已在执行的请求属于哪个模型。
4. 百分比若只显示整数，单个短关的差值容易受显示精度影响。同模型同设置做一小批关，
   再用总增量除以关数，得到包含必要工具调用开销的近似平均值。
5. Token 有逐调用 usage 时才汇总实测值；output 若已含 reasoning 不重复相加，
   cached input 若是 input 的子集也不重复相加。没有 usage 时只能记录估算。

不要依据公开的 credits 价格或消息数量估计反推出账户 5 小时固定 token 总额。
更换模型或设置后重新校准，保留首次工具准备与日常关卡制作的独立记录。
